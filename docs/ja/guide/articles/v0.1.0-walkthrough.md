# Dockerで2つの外向き通信境界を作る

![Agent Egress Lab v0.1.0 リリースヘッダー](/release-header-v0.1.0.svg)

Agent Egress Lab v0.1.0は、関連するものの意図的に分離した2つの実験を収録します。1つは許可リスト付きプロキシを通じてAgentの通信経路を制限し、もう1つはPlaywright Runnerから公開接続を取り除きながら内部テストアプリへの接続を維持します。

## なぜ2つの境界が必要なのか

ブラウザ実行を別コンテナへ移すだけでは、Agent本体が実行するコマンドを制限できません。反対に、Agentをプロキシ経由にしても、生成されたブラウザテストが公開ページへ接続できないことは証明できません。トポロジーを分離すると、それぞれの保証と不足が明確になります。

## 実験1：制御された1本の外向き経路

`sandbox`ネットワークは内部専用です。`agent-runner`と`egress-proxy`がこのネットワークを共有しますが、`outside`にも接続するのはプロキシだけです。Agentのプロキシ環境変数は、その唯一の経路を指します。

検証では、最初にプロキシを迂回して直接通信が失敗することを証明します。続いて許可済みGitHub APIをプロキシ経由で呼び出し、最後に未許可の接続先を呼び出して、クライアント側の失敗とプロキシログの`DENY`を両方要求します。

## 実験2：ブラウザから内部へだけ接続

Playwright Runnerとnginxデモアプリは、2つ目の内部ネットワークを共有します。このトポロジーにプロキシはありません。テストは内部ページの表示成功を証明した後、公開ページへの遷移失敗を必須とし、ブラウザエラーを記録します。

これは、生成されたE2Eコードに外部送信を促すプロンプトインジェクションが含まれる可能性がある場合に特に重要です。生成テストにどのような遷移コードが含まれていても、ネットワークがRunnerへ公開経路を与えません。

## 応用前に制限を確認する

CONNECTプロキシが判断するのは接続先であり、データ内容ではありません。許可済みAPIは依然として秘密情報を受信できます。また、Offline Runnerの境界はそのRunnerだけが対象であり、Agent本体のコマンドには別のegress policyが必要です。

[セキュリティモデル](../security-model)で自分の脅威モデルと保証範囲を対応付け、[はじめに](../getting-started)の手順で証拠を再現してください。
