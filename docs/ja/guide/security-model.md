# セキュリティモデル

## 目的

Agent Egress Labは、対象を絞った2つのワークロードに対するネットワーク制御を実演します。

- `agent-runner`は外部への直接経路を持たず、egress proxyを使用する
- `e2e-runner`は、同じDocker内部ネットワークに接続されたサービスだけへ到達できる

検証スクリプトは、同梱したCompose構成と指定されたテスト対象について、これらの性質を確認します。

![Offline E2Eのセキュリティ境界](../../architecture/offline-e2e-security-boundary.jpg)

## Agentの通信経路

`sandbox`ネットワークは`internal: true`で宣言されています。Agentのプロキシ環境変数は`egress-proxy`を指し、プロキシだけが`sandbox`と`outside`の両方へ接続します。`proxy.py`はCONNECTメソッドだけを受け付け、要求された`host:port`を`ALLOWED_CONNECT_TARGETS`と比較します。

これは接続先の許可リストであり、コンテンツ検査ではありません。許可済み接続先へのリクエストには、依然として機密データを含められます。

## オフラインブラウザの通信経路

`offline-e2e`ネットワークも`internal: true`ですが、二重接続のプロキシを持ちません。Playwright Runnerと`local-app`は同じネットワークを共有するため、内部ページは表示できます。Runner内では公開DNSの解決またはルーティングが失敗し、ブラウザレベルのエラー証拠が生成されます。

## 軽減する脅威

- Agentコンテナからの意図しない直接外向き通信
- 生成されたE2EコードによるOffline Runnerから公開接続先への遷移
- 設定済み`host:port`許可リストにない接続先へのプロキシ通信

## 対象外

- ペイロード検査やDLP
- 許可済み接続先自体の信頼性
- Agentがすでに利用できる認証情報
- Dockerホストや別ネットワークからの通信
- DNS pinning、高度なプロキシ堅牢化、IDベースポリシー、マルチテナント分離
- 本番運用の可用性、可観測性、インシデント対応

本番設計では、ネットワーク制御に加えて、スコープを絞った認証情報、リクエスト単位の認可、高影響操作の承認、監査ログ、レート制限、保守されたプロキシまたはゲートウェイを組み合わせてください。
