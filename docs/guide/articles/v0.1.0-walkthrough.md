# Building two outbound boundaries with Docker

![Agent Egress Lab v0.1.0 release header](/release-header-v0.1.0.svg)

Agent Egress Lab v0.1.0 packages two related but deliberately separate experiments. One constrains the agent's network path through an allowlisted proxy. The other removes public connectivity from a Playwright runner while preserving access to an internal test app.

## Why two boundaries?

Moving browser execution into another container is useful, but it does not constrain commands executed by the agent itself. Conversely, proxying the agent does not prove that generated browser tests are unable to reach public pages. Keeping the topologies separate makes their guarantees and gaps easier to see.

## Experiment 1: one controlled outbound path

The `sandbox` network is internal. `agent-runner` and `egress-proxy` share it, but only the proxy also joins `outside`. Proxy environment variables point the agent at that single path.

The verification bypasses the proxy once to prove direct egress fails, calls an allowlisted GitHub API target through the proxy, then calls an unlisted target and requires both a client failure and a `DENY` proxy log entry.

## Experiment 2: internal browser access only

The Playwright runner and nginx demo app share a second internal network. There is no proxy in this topology. The test proves the local page loads, then requires public navigation to fail and records the browser error.

This is especially relevant when generated E2E code may contain a prompt-injected request to send data externally. The network prevents that runner from obtaining a public route, regardless of what navigation call appears in the generated test.

## Read the limitation before adapting it

The CONNECT proxy makes a destination decision, not a data decision. An allowed API can still receive secrets. The offline runner boundary also applies only to that runner; agent-level commands need the separate egress policy.

Use the [security model](../security-model) to map these guarantees to your threat model, then follow [getting started](../getting-started) to reproduce the evidence.
